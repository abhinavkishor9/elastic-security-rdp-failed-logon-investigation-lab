# Troubleshooting Notes — RDP Failed Logon Investigation

## 1. No Event ID 4625 Initially

### Symptom

The initial Windows Security log search returned no Event ID `4625` events.

```powershell
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4625} -MaxEvents 20 |
Select-Object TimeCreated, Id, ProviderName, Message
```

### Check

Windows failed-logon auditing was checked:

```powershell
auditpol /get /subcategory:"Logon"
```

Initial result:

```text
Logon/Logoff
  Logon    No Auditing
```

### Resolution

Failure auditing was enabled:

```powershell
auditpol /set /subcategory:"Logon" /failure:enable
```

Verification:

```powershell
auditpol /get /subcategory:"Logon"
```

Result:

```text
Logon/Logoff
  Logon    Failure
```

A genuine failed authentication was then generated.

---

## 2. Enabling Auditing Did Not Create an Event

### Symptom

After enabling failure auditing, no new Event ID `4625` existed immediately.

### Explanation

Enabling auditing only allows Windows to record future failed authentication attempts.

It does not create a failed-logon event by itself.

### Resolution

A controlled failed authentication was generated:

```powershell
net use \\localhost\IPC$ /user:.\RDPBruteLab WrongPassword123!
```

Windows returned:

```text
System error 1326 has occurred.

The user name or password is incorrect.
```

Event ID `4625` was then generated.

---

## 3. RDP Logon Type 10 Search Returned No Results

### Query

```text
FROM logs-*
| WHERE event.code == "4625"
| WHERE winlog.event_data.LogonType == "10"
```

### Result

No matching documents were observed.

### Investigation

The generated Windows event contained:

```text
LogonType: 3
```

The controlled authentication was performed through:

```text
\\localhost\IPC$
```

This produced network authentication rather than RDP RemoteInteractive authentication.

### Conclusion

The lack of Logon Type `10` was consistent with how the test was performed.

It was not treated as an Elastic ingestion failure.

---

## 4. No Separate RDP Client

### Problem

The lab environment did not have a separate system available to act as an RDP client.

### Consideration

A genuine RDP brute-force investigation requires authentication attempts through RDP.

Using the same machine as both client and server would not provide the same evidence as a remote RDP authentication scenario.

### Decision

The lab was not extended using automated password-guessing tools.

No Hydra, Ncrack, Medusa, or similar tools were used.

No synthetic Windows events were generated.

The investigation continued using the genuine Event ID `4625` generated by the controlled network authentication.

---

## 5. RDP Port 3389 Was Not Observed Listening

### Check

```powershell
Get-NetTCPConnection -LocalPort 3389 -State Listen -ErrorAction SilentlyContinue
```

### Result

No listener was observed in the captured output.

The RDP registry configuration was checked:

```powershell
Get-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server" -Name fDenyTSConnections
```

Initial result:

```text
fDenyTSConnections : 1
```

RDP was temporarily enabled:

```powershell
Set-ItemProperty -Path "HKLM:\SYSTEM\CurrentControlSet\Control\Terminal Server" -Name "fDenyTSConnections" -Value 0
Enable-NetFirewallRule -DisplayGroup "Remote Desktop"
```

The Remote Desktop Services service was running:

```powershell
Get-Service -Name TermService
```

Result:

```text
Status   Name        DisplayName
------   ----        -----------
Running  TermService Remote Desktop Services
```

A separate RDP client was still unavailable, so the lab did not attempt to force an RDP authentication sequence.

## 6. Elastic Source IP Field Was Null

### Symptom

The raw Windows event contained:

```text
IpAddress: ::1
```

However, the Elastic query showed a null or empty value for:

```text
winlog.event_data.IpAddress
```

### Query

```text
FROM logs-*
| WHERE event.code == "4625"
| STATS failure_count = COUNT(*) BY winlog.event_data.IpAddress
| SORT failure_count DESC
```

### Interpretation

The raw Windows event contained the source address, while the parsed Elastic field did not expose it in the captured result.

The raw Windows event was therefore used as the authoritative evidence for this field.

This was documented as a field-mapping or parsing limitation rather than treating the source as unknown.

## 7. Null Target Account Group

### Query

```text
FROM logs-*
| WHERE event.code == "4625"
| STATS failure_count = COUNT(*) BY winlog.event_data.TargetUserName
| SORT failure_count DESC
```

### Result

```text
RDPBruteLab    1
(null)         1
```

The null target value was not automatically interpreted as another failed attack.

Each event requires individual inspection before assigning investigative meaning.

## 8. No Successful 4624 Event

### Query

```text
FROM logs-*
| WHERE event.code == "4624"
| WHERE winlog.event_data.TargetUserName == "RDPBruteLab"
| KEEP @timestamp, host.name, event.code, winlog.event_data.TargetUserName, winlog.event_data.LogonType, winlog.event_data.IpAddress
| SORT @timestamp DESC
```

### Result

No matching documents were observed.

### Interpretation

No successful Event ID `4624` for `RDPBruteLab` was observed in the searched Elastic data.

This does not establish that no authentication occurred outside the searched telemetry or time range.

---

## 9. Avoiding False Classification

The original investigation scenario focused on RDP brute-force activity.

The actual event contained:

```text
Event ID:                  4625
Target User:               RDPBruteLab
Logon Type:                3
Authentication Package:    NTLM
Source Address:            ::1
SubStatus:                 0xc000006a
```

The correct interpretation is:

```text
Failed network authentication
```

The event was not classified as:

```text
Confirmed RDP brute-force activity
```

The Logon Type was used to distinguish the actual authentication mechanism from the original investigation hypothesis.

---

## 10. Evidence-First Troubleshooting

The troubleshooting approach followed these principles:

- Validate the Windows audit configuration before troubleshooting Elastic.
- Generate genuine telemetry rather than synthetic events.
- Inspect raw Windows event fields before relying on parsed SIEM fields.
- Use Logon Type to identify the authentication mechanism.
- Do not interpret every Event ID `4625` as RDP activity.
- Do not interpret incomplete or null fields as evidence of malicious activity.
- Do not label activity as brute force without repeated authentication evidence.
- Document environment limitations instead of modifying the evidence.
